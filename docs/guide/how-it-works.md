# 工作原理

## 核心思路

一个文件要同时被两种格式的解析器接受，关键是让两种解析器**从相反方向**读取它：

```
┌───────────────────────────────────────────────────────────┐
│  PNG / JPEG 图像字节          │  ZIP 归档字节                │
│  ↓                            │  ↓                         │
│  解析器从头读到结束标记         │  解析器从尾部回退找 EOCD      │
│  （IEND / EOI 即停）           │  （End of Central Directory）│
└───────────────────────────────────────────────────────────┘
```

- **图像解析器**从头开始顺序读取，遇到 `IEND`（PNG）或 `EOI`（JPEG）就认为图片结束，完全忽略后面的字节。
- **ZIP 解析器**从文件末尾向前扫描，寻找 EOCD 记录（签名 `0x06054b50`），再由中央目录定位每个条目。

两条路径互不干扰，因此可以共存。

## 为什么不会互相破坏

### 图像侧

PNG 的 `IEND` 块是格式规定的结束标记，规范要求解析器在此停止。JPEG 的 `EOI`（`0xFFD9`）同理。追加的归档字节不会被当作图像数据 —— 图像查看器读到的是一张完全正常的图片。

### 归档侧

ZIP 的定位是**自末尾向前**的：

1. 从文件末尾向前搜索 EOCD 签名（最多回溯 65557 字节，以容纳最长注释）。
2. 从 EOCD 读出中央目录的大小与偏移。
3. 遍历中央目录的每条记录，得到文件名与数据位置。

因为整个归档被完整地追加在图像之后，ZIP 解析器从文件尾部一定能找到它。

## 偏移量重定位

这是实现中最关键的一步。

ZIP 内部有两处**绝对偏移**：

| 位置 | 字段 | 含义 |
| --- | --- | --- |
| EOCD + 16 | 中央目录偏移 | 中央目录相对归档起点的位置 |
| 中央目录记录 + 42 | 本地文件头偏移 | 每个条目的本地头相对归档起点的位置 |

其余字段（大小、CRC、名称长度等）都是相对的，不需要修改。

归档本来是独立构建的，偏移量以自身起点为 0 计算。当它被追加到图像之后时，这些偏移量必须整体加上图像长度，否则解析器会定位到错误的位置：

```
adjustment = 图像字节长度

EOCD.中央目录偏移        += adjustment
中央目录[i].本地头偏移    += adjustment
```

实现上，重定位后的缓冲区在归档前预留了 `adjustment` 个字节的空位，归档字节整体后移写入该位置，同时上述两类偏移量各自加上 `adjustment`。因此：

- 整个平衡文件里，本地文件头的物理位置 = 图像长度 + 归档内偏移。
- 把归档单独拿出来看时，偏移量与自身起点一致。

### 读取时的 concat 修正

由于偏移量是相对**归档起点**记录的，而 EOCD 记录了自己在**整个文件**中的绝对位置，标准 ZIP 工具会用下式反推出前缀长度：

```
prefix = EOCD绝对位置 - 中央目录大小 - 中央目录偏移
```

这正是 `unzip` 提示 `N extra bytes at beginning or within zipfile` 时所做的修正，Python 的 `zipfile` 模块、7-Zip 也采用同样逻辑。加上这个前缀后，偏移量即为绝对位置，归档在**独立解析**和**作为 polyglot 一部分解析**两种情形下都能被正确读取 —— 本项目的解析器同样实现了该修正。

> 自解压归档（SFX）和 `.jar` 的 `zip -A` 修复走的都是同一套机制，因此该文件对第三方工具是**标准兼容**的，而非需要特殊处理。

## 兼容性矩阵

引擎通过「前端格式 × 后端格式」的兼容规则表决定某个组合是否支持：

| 前端 | 后端 | 支持 | 模式 |
| --- | --- | --- | --- |
| PNG | ZIP | ✅ | `relocated` |
| JPEG | ZIP | ✅ | `relocated` |
| 其他组合 | — | ❌ | `unsupported` |

`relocated` 表示「通过偏移量重定位实现」。未注册的组合一律视为 `unsupported`，`create()` 会直接抛出 `Unsupported back format` 错误而不是产出损坏的文件。

## 安全边界

读取归档时会施加多重限制，详见[安全模型](/guide/security)：

- 条目数量上限（默认 10000）
- 单条目解压后大小上限（默认 1 GiB）
- 总解压大小上限（默认 10 GiB）
- 路径穿越拦截（`..`、绝对路径、`.`）

## 浏览器端实现

`@polyglot/browser` 是同一套算法的纯 `Uint8Array` 移植，不依赖 Node 的 `Buffer`：

- CRC-32 查表实现在模块加载时构建一次
- PNG / JPEG 解析直接操作 `Uint8Array` 与 `DataView`
- ZIP 构建与偏移量重定位逻辑与 Node 端保持一致

[Playground](/playground) 完全由它驱动，所有处理都在浏览器本地完成，**文件不会上传到任何服务器**。
