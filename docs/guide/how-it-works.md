# 工作原理

## 核心思路

一个文件要同时被两种格式的解析器接受，关键是让两种解析器**从相反方向**读取它：

```
┌───────────────────────────────────────────────────────────┐
│  PNG / JPEG 图像字节          │  ZIP 归档字节                │
│  ↓                            │  ↓                         │
│  解析器从头读到结束标记         │  解析器从尾部回退找 EOCD      │
│  （IEND / EOI 即停）           │  （End of Central Directory）│
└───────────────────────────────────────────────────────────┘
```

- **图像解析器**从头开始顺序读取，遇到 `IEND`（PNG）或 `EOI`（JPEG）就认为图片结束，完全忽略后面的字节。
- **ZIP 解析器**从文件末尾向前扫描，寻找 EOCD 记录（签名 `0x06054b50`），再由中央目录定位每个条目。

两条路径互不干扰，因此可以共存。

## 为什么不会互相破坏

### 图像侧

PNG 的 `IEND` 块是格式规定的结束标记，规范要求解析器在此停止。JPEG 的 `EOI`（`0xFFD9`）同理。追加的归档字节不会被当作图像数据 —— 图像查看器读到的是一张完全正常的图片。

### 归档侧

ZIP 的定位是**自末尾向前**的：

1. 从文件末尾向前搜索 EOCD 签名（最多回溯 65557 字节，以容纳最长注释）。
2. 从 EOCD 读出中央目录的大小与偏移。
3. 遍历中央目录的每条记录，得到文件名与数据位置。

因为整个归档被完整地追加在图像之后，ZIP 解析器从文件尾部一定能找到它。

## 偏移量重定位

这是实现中最关键的一步。

ZIP 内部有两处**绝对偏移**：

| 位置 | 字段 | 含义 |
| --- | --- | --- |
| EOCD + 16 | 中央目录偏移 | 中央目录相对文件起点的位置 |
| 中央目录记录 + 42 | 本地文件头偏移 | 每个条目的本地头相对文件起点的位置 |

其余字段（大小、CRC、名称长度等）都是相对的，不需要修改。

归档本来是独立构建的，偏移量以自身起点为 0 计算。当它被追加到图像之后时，这些偏移量必须整体加上图像长度，否则解析器会定位到错误的位置：

```
adjustment = 图像字节长度

EOCD.中央目录偏移        += adjustment
中央目录[i].本地头偏移    += adjustment
```

实现上，重定位只重写这两类指针，**归档字节本身保持原样**（长度不变）。因此：

- 整个平衡文件里，本地文件头的物理位置 = 图像长度 + 归档内偏移（即归档紧跟在图像之后，中间没有任何填充）。
- 把归档单独拿出来看时，偏移量等于自身起点加上图像长度，仍然一致。

这正是 Info-ZIP `zip -A` 对自解压归档（SFX）所做的修正——把偏移量改成相对文件起点的绝对位置，从而让**不做任何补偿**的解析器也能直接定位。

::: tip 为什么必须这样做
早先的实现改为在归档前预留 `adjustment` 字节的空位，结果是文件中出现「双重前缀」：偏移量是图像相对值，而归档物理上又向后挪了一个图像长度。实测后果是 `unzip`/`zipinfo` 报警告、**7-Zip 直接拒绝打开整个文件**，且体积翻倍。改成不垫字节后，同一组样本从 16 项检查通过 / 8 项失败变为 23 项全部通过。详见[兼容性实测](/guide/compatibility)。
:::

### 读取时的 concat 修正

ZIP 规范允许文件在归档数据之前带有任意前缀（例如自解压 stub）。标准工具会用 EOCD 反推出前缀长度：

```
prefix = EOCD绝对位置 - 中央目录大小 - 中央目录偏移
```

由于本实现的偏移量是绝对位置，解析**整个文件**时该公式算出 `prefix = 0`，工具直接按记录偏移定位即可，不会出现任何警告。本项目的解析器同样实现了该修正，因此无论喂给它整个平衡文件还是「跳过图像后的归档子串」，都能正确解析。

### 兼容性边界（重要）

解析器大致分两类：

| 类型 | 行为 | 代表 |
| --- | --- | --- |
| 按记录偏移定位 + 可选 concat 修正 | ✅ 可打开 | `unzip`/`zipinfo`、Python `zipfile`、libarchive（`bsdtar`、macOS 归档实用工具）、7-Zip |
| 要求文件第 0 字节就是 `PK\x03\x04` | ❌ 拒绝 | Apple `ditto`（含 Finder 部分解压流程）、部分严格 GUI 工具 |

第二类是**格式层面的互斥**：PNG/JPEG 的签名必须占据第 0 字节，ZIP 就不可能同时占据第 0 字节。因此任何「必须从第 0 字节看到 ZIP」的消费者永远无法打开图片前端的 polyglot 文件——这不是实现缺陷，而是这种文件形态的固有边界。**请勿将「所有压缩软件都能打开」作为目标**；`tests/compatibility/third-party.test.ts` 用真实工具锁定了第一类兼容性。

## 支持的组合

引擎通过「前端格式 × 后端格式」的兼容规则表决定某个组合是否支持：

| 前端 | 后端 | 支持 | 模式 |
| --- | --- | --- | --- |
| PNG | ZIP | ✅ | `relocated` |
| JPEG | ZIP | ✅ | `relocated` |
| 其他组合 | — | ❌ | `unsupported` |

`relocated` 表示「通过偏移量重定位实现」。未注册的组合一律视为 `unsupported`，`create()` 会直接抛出 `Unsupported back format` 错误而不是产出损坏的文件。

具体哪些第三方工具实测可以正常解压、哪些不行，见[兼容性实测](/guide/compatibility)。

## 安全边界

读取归档时会施加多重限制，详见[安全模型](/guide/security)：

- 条目数量上限（默认 10000）
- 单条目解压后大小上限（默认 1 GiB）
- 总解压大小上限（默认 10 GiB）
- 路径穿越拦截（`..`、绝对路径、`.`）

## 浏览器端实现

`@polyglot/browser` 是同一套算法的纯 `Uint8Array` 移植，不依赖 Node 的 `Buffer`：

- CRC-32 查表实现在模块加载时构建一次
- PNG / JPEG 解析直接操作 `Uint8Array` 与 `DataView`
- ZIP 构建与偏移量重定位逻辑与 Node 端保持一致

[Playground](/playground) 完全由它驱动，所有处理都在浏览器本地完成，**文件不会上传到任何服务器**。
